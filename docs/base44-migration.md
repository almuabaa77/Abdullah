# ترحيل البيانات من Base44

يعمل الترحيل من سطر الأوامر في نسخة المشروع. التطبيق اليومي لا يتصل بـ Base44. استخدم مجلدات خاصة خارج المستودع للاحتفاظ بالمدخلات والنسخة والتقارير ونسخة MySQL. احفظ نسخة مشفرة منها في تخزين منفصل خاضع لإدارة المنصة.

## المدخلات من Base44

- يسترجع مسار API تعريف OpenAPI ومخططات الكيانات تلقائيًا إن كانت الصلاحيات تسمح. إن قدمت نسخة محلية، ضع JSON باسم `openapi.json` في مجلد المدخلات للمقارنة.
- من **Data** صدّر كل جدول من بيئة **Production** بدون مرشحات، خصوصًا جداول المستخدمين والحلقات والطلاب والحضور والتسميع والنقاط والاختبارات. ضع الصادرات في `tables/EntityName.json` أو `tables/EntityName.csv` مع استخدام اسم الكيان كما يظهر في API. صدّر **App Users** أيضًا إن لم يمكن قراءة كيان `User`.
- ضع الملفات الأصلية والصور والتسجيلات في `files/`. ضع فهرس الربط `assets.json` في المجلد نفسه الذي يحتوي `openapi.json`. يحتوي على مصفوفة عناصر على هيئة `{"sourceUri":"original-file-reference","file":"folders/document.pdf"}`. استخدم `[]` بعد التحقق من عدم وجود ملفات. تُنسخ الملفات نفسها إلى الأرشيف وتُفحص ببصمة SHA-256. تعرض المعاينة الروابط المحتملة للملفات في `asset-references.json`. يُسمح بتمييز الروابط الخارجية الدائمة والمراجعة صراحةً عبر `"external":true`.
- ضع نسخة الكود المتاحة من **Export project as ZIP** أو المستودع السابق ضمن المدخلات. أضف تصديرًا مستقلًا للأتمتة والسجل التاريخي ونسخ **Backup & Restore** وسجل المحذوفات إذا كانت قابلة للتصدير. احتفظ بهذه الملفات خارج مجلد `tables` حتى تبقى تاريخًا منفصلًا. لا تستعد سجلات محذوفة في المصدر لأجل التصدير.
- في مسار API استخدم **Personal access token → One app → Read-only** واضبطه كمتغير سري مؤقت `BASE44_PERSONAL_ACCESS_TOKEN`. الصادرات اليدوية بديل، وتغلب على API لكل جدول عند توفرها. تحقق من الأعداد من لوحة Base44 حيث لا يتاح عدّ API، خصوصًا `User` والسجل التاريخي. نسّق نافذة ثابتة للتقاط نسخة متسقة قبل القطع النهائي. يكشف فحص العدّ الزيادة والنقصان، وقد لا يكشف تعديل المحتوى مع بقاء عدد السجلات نفسه.

لا تشمل صلاحيات Base44 تلقائيًا سجلات سبق حذفها نهائيًا أو ملفات محمية غير قابلة للتصدير. وثّق كل فجوة في تقرير الاعتماد.

يجرد مسار API الأتمتة المتاحة ويصدّر تعريفاتها والكود من نقاط القراءة المتاحة. يجلب الملفات العامة من نطاق وسائط Base44 الخاص بمعرّف التطبيق من دون تمرير رمز الوصول. الملفات الخاصة أو الروابط الخارجية أو عناصر المكتبة التي تتجاوز حدود التعداد تبقى فجوات موضحة إلى أن يتاح مصدر قراءة مشروع لها.

## الالتقاط والتحقق والمعاينة

```sh
npm run migration:base44 -- capture --draft --app APP_ID --input /private/input --out /private/source
# بعد مراجعة فهرس المرفقات وإضافة ملفاتها، كرر الأمر دون --draft
npm run migration:base44 -- capture --app APP_ID --input /private/input --out /private/source
npm run migration:base44 -- verify --archive /private/source
npm run migration:base44 -- pack --archive /private/source --out /private/base44-backup.tar.gz
npm run migration:base44 -- snapshot --out /private/current
npm run migration:base44 -- preview --archive /private/source --snapshot /private/current/workspace.json --out /private/review
```

يقرأ `snapshot` مساحة `school` باستخدام `MIGRATION_DATABASE_URL` من متغير بيئة. استخدم حساب قراءة في هذه المرحلة. يستأنف الالتقاط صفحات API الموجودة إذا انقطع الاتصال قبل إغلاق النسخة. عند تغيير المدخلات أو البيانات أثناء الالتقاط، استخدم مجلدًا جديدًا. بعد ختم الأرشيف يحفظ البيان قائمة الملفات وبصماتها والأعداد والجداول أو الملفات غير المتاحة. يمكن نقل المجلد إلى تخزين مستقل مع المحافظة على محتواه كاملًا. ينشئ `pack` ملفًا مضغوطًا قابلًا للتنزيل وبصمة منفصلة. للاستعادة خارج الخدمة، فك الملف إلى مجلد خاص ثم شغّل `verify` واستخدم ملفات البيانات والمرفقات مباشرة. استخدم قناة تنزيل خاصة وتخزينًا مشفرًا للنسخ التي تحتوي بيانات الطلاب.

يسرد التقرير الحقول وأعدادها وأنواعها، يقترح الإسناد للأقسام الحالية، ويعرض معرّف المصدر والوجهة ونتيجة مراجعة كل صف. قيم الحقول الأصلية موجودة في النسخة الخاصة. أضف `--mapping /private/mapping.json` وشغّل المعاينة في مجلد مراجعة جديد بعد اعتماد المطابقة. يربط المخطط `fields` اسم الحقل في التطبيق الحالي بمساره في المصدر، ويربط `refs` العلاقات باسم جدول المصدر. استخدم `values` لتحويل قيم الحقول صراحة و`matches` لمراجعة ربط معرّف مصدر بمعرّف موجود. مثال مختصر

```json
{
  "User": {
    "target": "users",
    "fields": {"name": "full_name", "phone": "phone", "role": "school_role"},
    "values": {"role": {"instructor": "teacher", "guardian": "parent"}}
  },
  "Halaqa": {
    "target": "circles",
    "fields": {"name": "title", "teacherId": "teacher_id", "days": "days"},
    "refs": {"teacherId": "User"}
  }
}
```

المطابقات المدعومة حاليًا تشمل التعرف على حسابات Firebase الحالية، والحلقات والطلاب، والسجل اليومي التاريخي، والروابط العائلية، ونتائج الاختبارات السابقة. تُراجع الاختلافات في الحسابات بالهاتف والدور والاسم أو معرّف معتمد. إنشاء حسابات جديدة ودعوتها يتم عبر نظام التطبيق الحالي بعد مراجعة تقرير المصدر. يُحفظ المحتوى والحقول خارج هذه المطابقات في الأرشيف لحين تحليلها وتطوير وظائفها حسب الأصول.

## التطبيق عند اعتماد الخطة

احتفظ بنسخة المصدر ونسخة قاعدة التطبيق وتقرير المعاينة. نفّذ التطبيق فقط بعد اعتماد المستخدم لخطة بعينها وبصمتها، وبعد نشر حماية السجلات التاريخية. يتطلب الأمر `apply` نفس مسارات الأرشيف ونسخة مساحة العمل ومجلد التقرير، بالإضافة إلى `--approve` متبوعًا ببصمة الخطة و`--keep-archived` عند اعتماد بقاء محتوى خارج العرض المباشر. يكتب إيصالًا محليًا ويستخدم تبديلًا ذريًا مشروطًا بإصدار MySQL. تتوقف العملية عند غياب جداول أو ملفات، أو وجود تعارضات، أو تغير نسخة مساحة العمل عن المعاينة. ترسل السجلات التاريخية مباشرة إلى مخزن البيانات بدون قائمة إشعارات، وتحمل سجلات التسميع علامة تمنع دخولها في محركات الاستحقاق الآلي.

يستخدم `rollback` بصمة الخطة ونسخة مساحة العمل ومجلد التقرير، ويستعيد النسخة الأصلية إذا بقي إصدار البيانات بعد الترحيل مطابقًا للإيصال. إذا حدثت كتابة أحدث، يتوقف حفاظًا عليها ويتطلب العمل على نسخة استعادة منفصلة وإعداد تسوية مراجَعة. افحص النتائج قبل إعادة فتح الكتابة بعد القطع.
